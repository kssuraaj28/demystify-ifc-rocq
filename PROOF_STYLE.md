# Proof Style

## ssreflect conventions

- We use ssreflect freely.
- Use `Set Default Goal Selector "!"` for easier proof repair. Do not use the
  `all:` goal selector — write the goal numbers explicitly.
- Have good discipline with autogenerated names. It is okay to `Unset
  SsrIdents` while discovering a proof; finished proofs should not have this.
- Do not use the `by`, `first`, or `last` ssr tacticals. `by` does too much;
  its terminating behaviour is enforced better by the system (via the goal
  selector and strict-subproofs settings). Use `cycle` for `last first`. Use
  `[ t |..]` for `first t`, etc.
- Do not use `intro`; use `move`, for uniformity.
- Do not use `destruct`; use ssr `case`. Use ssr `elim` instead of `induction`.
- For finishers, do whatever you want.
- All rewriting tactics are fine (ssreflect, normal, etc.). Normal `rewrite`
  can rewrite under binders.

# `harden`

Wrap user-defined tactics with `harden` so a goal-count mismatch surfaces as a
clear failure instead of silent misbehaviour. It demands a single focused goal
on entry.

- `harden n t` / `harden <= n t` / `harden ? t` — throw on mismatch. Use when a
  wrong count indicates a programmer error. `harden ?` places no count
  constraint.
- `precise_harden t goals allow_hyps_change` is the underlying primitive
  (`goals : (int * bool) option`, where the bool is "≤ vs =").
- You may have to prefix a tactic with `idtac;` to prevent eager evaluation
  (see https://rocq-prover.zulipchat.com/#narrow/channel/237977-Rocq-users/topic/Weird.20bug/with/593251599).

# `cook`

`cook` is the project automation tactic, defined in `Tacs.v` (`Module Cook`).
It runs the registered tactics (the "cookbook") over the focused goals until
every goal is solved or all tactics fail on it.

- `cook` runs to completion. Goals are consumed depth-first. Panics if no
  registered step ever succeeds (so a cook that makes no progress fails loudly).
- `cook_step` runs one pass over the registered chain on a single focused goal,
  applying the first tactic that succeeds.
- `cook_debug : int` controls tracing (0 = silent; higher = more detail). Set
  with `Ltac2 Set cook_debug := 1.`
- Clients can also drive the chain through the `cook_step` HintDb via
  `auto with cook_step`.

Registered steps are appropriately hardened (goal-count and
hypothesis-preservation guards are applied automatically); see `Tacs.v` for the
exact contract.

## Registering cookbook steps

Register with `add_cookstep ltac1:(<tactic>) "<name>" old`:

```coq
Ltac2 Set this_cookbook_ as old :=
  add_cookstep ltac1:(rewrite -> Forall_map) "Forall_map" old.
```

- The description string should match the underlying lemma/tactic name so debug
  output is readable.
- **Use `rewrite ->` (vanilla Rocq rewrite), not bare ssr `rewrite`, in rewrite-based cooksteps.** ssr's keyed matching can leave the
  goal scarred — delta-unfolding the redex while still failing to substitute —
  whereas the vanilla form is more predictable for cookbook use. Motivating case:
  `rewrite public_mk` unfolding `compute_new_pc_opt` to look for `mk_lbl _ _`
  inside, then leaving the unfold even though the substitution didn't fire.
- Cookbook management: `create_new_cookbook`, `join_cookbooks`, `keep_only`,
  `delete`. `curr_cookbook` is the active chain; change it with
  `Ltac2 Set curr_cookbook`.

When a step boils down to "rewrite a normalization equality", prefer writing a
plain lemma and registering `rewrite -> <lemma>`. For lemmas whose RHS is just
the `cbn`-normalized LHS, the `cbn_eq` Ltac2 notation builds the equality type
for you. (Do not use `rewrite … in *` in a cookstep — it mutates hypotheses,
which the cookstep guards forbid; see `Tacs.v`.)

### Cookbook re-Import

`Ltac2 Set` declarations replay on every `Import` of the file. Without care, a
file imported twice doubles the chain. Avoid this by following each
`#[local] Ltac2 mutable this_cookbook_ := create_new_cookbook.` with a redundant
reset:

```coq
#[local] Ltac2 mutable this_cookbook_ := create_new_cookbook.
Ltac2 Set this_cookbook_ := create_new_cookbook.
```

The reset is itself a `Set` and replays on Import, wiping any previously
accumulated chain before the registration `Set`s re-accumulate. The result is
idempotent under repeated `Import`.

# Statement keywords

Rocq treats `Theorem`, `Lemma`, `Fact`, etc. identically; we use the keyword to
signal a statement's role:

- `Theorem` — headline / exported results (e.g. `extract_step_commute`).
- `Lemma` — substantive results you reason with directly.
- `Fact` — statements meant to be used via `cook`: registered in a cookbook
  (`add_cookstep`). You *can* apply a `Fact` by hand, but the intended use is
  through `cook`.

Rule of thumb: if it is registered as a cookstep, it is a `Fact`; otherwise it
is a `Lemma` (or `Theorem`). The keyword reflects intent, so it is readable off
the statement and does not change as incidental hand-uses come and go.
